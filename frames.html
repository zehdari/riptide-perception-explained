Mapping · Chapter 9

Frames, targets and the mission tree

Everything mapping knows leaves it as TF frames and covariances. Autonomy drives to the frames and waits on the covariances, and in return tells mapping which props to look for.

The short version
  • Mapping publishes every prop as a TF frame, like torpedo_frame, plus a pose with covariance. Autonomy drives to frames and waits for covariances to get small.
  • The behaviour tree decides what mapping may update. It sets a target (one prop or a list), and can lock the map so nothing changes while Talos shoots or grabs.
  • RepairCompMpcTree runs the tasks in order, each wrapped so that a failure just moves on to the next task with whatever the map has.
  • The gate is never mapped (it flies through the prior), the slalom, torpedo, baskets and bins are, and the table is fit to its two baskets only if both converge.

The estimator of Chapters 7 and 8 sits inside a ROS node, mapping.py. This chapter is the node's interface: the frames it publishes, the services autonomy calls, what a published covariance means and how the behavior trees in riptide_autonomy read it. It ends with the three prop-specific pieces of code that sit next to the estimator: the bins' binary classifier, the table fit and the bin geometry fit.

The frame tree

Three transforms stand between Talos and a prop. Odometry puts Talos in the odom frame, which is published as identical to world (the launch file says "until we get SLAM"). The AprilTag calibration sets world → map: before a run, Talos looks at the tag board on the pool wall, and a chameleon_tf node averages the observed tag pose and adopts it, with x, y and yaw free and z, roll and pitch locked (mapping.launch.py). After that, map is the odometry frame re-anchored once to the course; it moves with odometry and drifts with it.

Mapping then publishes map → offset, a pure translation: where the course sits in that drifting frame (Chapter 8). Every map-parented object's frame hangs off offset at its prior plus its deviation, and every other object's frame hangs off its parent's frame. Each object X gets the frame X_frame.

The parent of each object is init_data.<object>.parent in the config. Changing an object's parent between map and another frame changes the estimator's layout (a map object is in the course solve, a child has its own filter), so mapping only applies it at the next mapping/reset_mapping. Changing a prior's pose at runtime applies at once: the object jumps to the new prior and forgets its detections (param_callback).

What gets fused

Mapping does not fuse every detection it receives. The detector makes mistakes: in Nereus it reported a slalom pole on one of the gate's legs, where there is none (Chapter 3), and lookalike props get each other's class (one fire symbol for another). So only the objects autonomy is looking for are fused (vision_callback):

  • Targets, set with the mapping_target service. It takes one object or a comma-separated list, "fire_hole_large, fire_hole_small"; every listed object is fused and the first is the primary target. Setting a target resets it (Chapter 7): a well-known object keeps its estimate and needs 3 agreeing detections to be confirmed again, anything else needs 10 from its prior covariance. Its position is kept either way.
  • Background targets, set with mapping/set_background_targets, are fused alongside whatever the target is and are never reset by a target change. A search for one table item maps the others it happens to see. Detections of a background object say where it is but don't confirm it.
  • No target: only the closest detected object at least 1 m away is fused (closest_object).
  • lock_map in the same request stops all fusion. The competition tree locks the map from the start until the slalom, so that false slalom detection at the gate never reaches the map, and again between tasks and while it shoots, drops or grabs, so the frame it is aligning to can't move under it.

A detection also has to clear confidence_cutoff, 0.2 in the config. The detector's own thresholds (0.65 forward, 0.8 down) are already higher, so on Talos this cut never removes anything. Each fused detection flashes the LEDs green. A detection whose camera-to-parent transform isn't in TF yet is queued and retried every 125 ms for up to 2 s, then dropped with an error.

mapping/reset_mapping throws everything away: a fresh estimator from init_data, no targets, the classifier stopped, every frame back on its prior.

What is published

After every detection message, and at least every 2 s otherwise, mapping publishes for every object a PoseWithCovarianceStamped on mapping/<object>, in its parent frame, and the matching TF (publish_pose). It also publishes state/mapping (the targets and lock_map) and mapping/fused: the objects a detection was just fused into, as "bin_target1,helmet", so autonomy knows an object is in view even when the detector calls it something else.

The covariance is the uncertainty of the estimate, not the spread of recent detections. For a map object it includes the offset's uncertainty, so a prop seen once long ago reads as less certain the farther Talos has travelled since. Some rules shape it:

  • Unconfirmed objects report "not seen". Until fresh detections have confirmed an object since its last reset, its position variances are raised to at least 1.0 m² and the angle variances to 0.1 rad². These are the numbers the old mapping reported for an object it had no data on, so every behavior tree's covariance check still means "seen and settled".
  • Orientation. Mapping estimates yaw only: the published orientation is a pure yaw. Objects with lock_orientation_to_config keep their prior yaw. Objects with point_yaw_at_parent (the table items) are published facing their parent's origin, the table's centre. Downward-camera objects (the bin and its targets, the table) have the detected orientation thrown away before fusing.
  • Output slew, off. output.max_speed and output.max_yaw_rate_deg can make published frames slide toward the estimate instead of jumping, with the distance still to go added to the covariance. Both are 0 on Talos: the MPC already smooths frame motion itself (path.frame_speed on a carried path, its motion profile for setpoints), and a second filter would only add lag.

How the behaviour tree talks to mapping

Four nodes in riptide_autonomy talk to mapping. Everything the tree knows about where props are comes from TF frames and these four.

NodeWhat it does
SetMappingTargetCalls mapping_target with target_object and lock_map; fails if the call doesn't return within time_limit_secs.
getCovarianceWaits up to 5 s for the next mapping/<Target> message and outputs its error (below).
MapConvergedSucceeds once every object in a comma list has an error below target_cov. Answers immediately, so it can stop a running search the moment the estimate settles. It only trusts messages received after it started being ticked, so an estimate from before a target reset can't pass it.
SeenRecentlySucceeds if the object was detected at or above min_score (0.2) within max_age_secs, from the detector's topic or from mapping/fused.

The error both covariance nodes compute is not a distance. It is the root of the summed squares of the six diagonal variances, the angular ones divided by 2π:

e = \sqrt{\sigma_x^4 + \sigma_y^4 + \sigma_z^4 + \frac{\sigma_\phi^4 + \sigma_\theta^4 + \sigma_\psi^4}{2\pi}}

So it has units of m², and for a round position estimate e \approx \sqrt3\,\sigma^2. An unconfirmed object scores \sqrt{3 + 3 \cdot 0.01/2\pi} = 1.73, which is the "1.73" the config comments mention. Read the threshold as "how well the tree wants to know it". The error is in m², not metres: 0.0005 m² means about 1.7 cm of standard deviation, 0.0025 about 4 cm, 0.3 about 42 cm, and anything that is still unconfirmed sits at 1.73 no matter how many detections it has had.

RepairCompMpcTree, task by task

The competition tree, RepairCompMpcTree.xml, is long (about 4 100 lines) but its shape is simple: it runs the tasks one after another, and wraps each one in ForceSuccess. So when a search times out or a covariance check fails, that task ends and the mission carries on to the next one with whatever the map has. Nothing ever calls mapping/reset_mapping. This is what each task asks of perception.

Most of the searching happens in three subtrees, and they share a pattern.

  • MiniSearchMpc (slalom, magnets): park the forward camera a fixed distance in front of the prior, set the target, wait 5 s, then poll the covariance once a second until it passes or the time runs out. No search pattern.
  • SearchMpc (torpedo): set the target and sweep arcs around the estimate, panning. The moment SeenRecently (detected in the last 0.5 s) or MapConverged passes, it stops sweeping, centres the detection in the image, and holds until the map converges or the prop has been out of sight for 2 s. If nothing has been seen for 20 s it widens the sweep.
  • DownwardSearchMpc (baskets, table items, bins): skip if the covariance already passes. Otherwise set the target, fly the down camera to a hover height over the estimate, follow the detections while they keep coming, and when they stop for 3 s, spiral out from 0.25 m to 2 m around the estimate and try again, until the timeout.

The searches steer by mapping's frame, not by the raw detection: "following the detection" means re-aiming at warning_frame every half second. That frame only moves once mapping has accepted detections, and a brand-new target only accepts them once four agree (Chapter 7). If the estimate starts far enough off that the camera only ever catches the prop at the edge of its view, the two wait on each other. That is exactly how the warning basket was lost in Chapter 10.

Things to watch

Reading the tree next to mapping's code turns up a few weak spots. None of them broke the Nereus runs outright, but each can.

  • The table check is one second long. Both baskets must pass MapConverged at 0.0005 within a single 1 s window right after the two searches, and it is never retried. If one basket is briefly over, there is no table fit and every table item stays at its prior relative to an unfitted table.
  • Pickups 2–4 may not refine. DownwardSearchMpc skips setting the target when a background target has already brought the item under 0.5. But the map is still locked from the previous drop, so the 5 s hover check before the grab sees no new detections and the claw aligns on the older estimate.
  • The bins can block the magnets. If start_binary_classifier_second or stop_binary_classifier fails, the classifier is left running; the magnet task's start_binary_classifier then fails with "already running" and the magnet task is skipped. The magnet classifier is never stopped at the end either.
  • The slalom assumes the forward camera. Nothing sets the camera before the torpedo task; the slalom search relies on the detector starting on ffc.
  • The gate is flown from the prior. Its searches are commented out (an AlwaysFailure in front of them) and the map is locked, so a course that has moved shifts the gate pass with it until some other prop is mapped. The same goes for the return through the gate at the end.

Two identical targets: the binary classifier

The bins task has two targets that look the same to the down camera: two fire vinyls in the bin. The detector calls both fire, and mapping has to turn them into two objects, bin_target1 and bin_target2, without ever confusing one for the other. While the binary classifier runs, it replaces the normal fusion: detections of its class go into a buffer, and the classifier decides which instance each belongs to before the estimator sees it (binary_classifier.py).

  1. mapping/start_binary_classifier (class, instance 1, instance 2) resets both instances and starts acquire_first. Every detection goes into a rolling buffer (at most 500, each dropped after 8 s).
  2. Once some cluster in the buffer is dense enough, its centroid becomes instance 1 (track_first). From then on a detection within 0.2 m of it is fused into instance 1 and nudges the centroid (an exponential average, α = 0.15); anything else is rejected.
  3. Autonomy can freeze the buffer while it does the first target. Frozen, nothing is added or aged out, so the detections of the second vinyl already gathered survive however long the first task takes. Instance 1 still tracks.
  4. mapping/start_binary_classifier_second starts acquire_second: right away it looks for a cluster among the buffered detections at least 0.4 m from instance 1. Live detections within 0.3 m of instance 1 are rejected from then on. If one is there it is locked as instance 2 at once (track_second), and its frame appears in TF before Talos even turns toward it.
  5. mapping/stop_binary_classifier returns to normal fusion.

A cluster is found by greedy mode-seeking: the detection with the most neighbours within 0.15 m wins, and its neighbours are the cluster. It needs at least 6 detections. The farthest 10 % from the cluster's median are dropped before averaging (when there are a couple to spare), and a cluster whose mean squared spread is over 0.02 m² is rejected as not one object. Distances are horizontal only: for a flat target seen from above, depth is the noisiest axis. When an instance locks, mapping seeds its estimate on the centroid so the frame jumps there instead of crawling from the prior, and every detection the classifier passes on counts as already agreed (Chapter 7's acquisition check is skipped).

The classifier never uses the bin's layout: it would work the same with the vinyls anywhere. What it can't do is tell which vinyl is which, so instance 1 is simply the first that forms a dense cluster, usually the one Talos is over.

Fitting the table to its baskets

The table carries two baskets, helmet and warning, and smaller items, all children of table_frame. The baskets are what Talos can find most reliably, so after mapping them, autonomy calls mapping/center_table_on_baskets (center_table_on_baskets_callback). It moves and turns the table so the two measured baskets sit at their config offsets from it: the yaw lines the measured basket-to-basket axis up with the configured one, and the shift puts their midpoint where the config's midpoint is. A yaw correction over 30° is skipped (a basket was probably mapped wrong). Baskets and table items already seen are re-expressed in the new table frame so they stay where they were seen in the world; unseen items are still priors relative to the table, so they move with it. From then on the baskets are pinned: further detections no longer move them, and retargeting them doesn't reset them.

The tree only calls it when both baskets pass MapConverged at 0.0005 within one second of the second basket search. On the exact-course Nereus run it did, and mapping logged Moved table by (-0.036, 0.033, -0.000) in map to fit the baskets, yawed table 0.3 deg; kept pill, plug, nut_and_bolt, bandage where they were seen. On the moved-course run the warning basket was never acquired, the tree logged helmet,warning, not both converged below 0.0005: the table keeps its prior, and the table was never fit (Chapter 10).

This replaced an older approach that is still in the detector: with set_table_pair_enabled on, a frame showing both the warning and helmet symbols produced one combined table detection. The competition tree switches it off before and after the basket searches, so it never runs.

The bin geometry fit

One more piece sits beside the estimator, and its own comments call it a temporary competition hack ("cursed", "delete this after comp"): bin_geometry.py. After the binary classifier has placed the two targets, mapping/fit_bin_geometry fits the bin's CAD model to them: two vinyl correspondences give an x, y and yaw in closed form (with the configured yaw breaking the 180° ambiguity), refused if the measured baseline differs from the CAD one by more than 10 cm or the residual is over 10 cm. Height comes from the two vinyls when they agree within 10 cm and from the config otherwise. The fit seeds bin_cad_geometry, whose children (the magnets and their drop targets) then sit where the CAD puts them, with a published variance of at least 0.0025 m².
