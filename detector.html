Vision · Chapter 3

The detector, frame by frame

Everything Talos knows about the course starts as a colour image and a depth image from one of two stereo cameras. One node, yolo_orientation, turns each pair into named objects with 3D poses.

The short version
  • About ten times a second, take the newest colour image from the active camera and the depth image from the same moment.
  • Run YOLO (Chapter 2): a class, confidence, box and mask per object.
  • Turn each mask plus depth into a 3D pose (Chapters 4 and 5) and send them all to mapping.
  • The detector is sometimes wrong; mapping, not the detector, filters that out.

This chapter follows one frame through the tensor_detector node: yolo_orientation.py is the ROS side, yolo_model.py wraps the network and detection.py makes poses. Every frame here comes from a full Nereus simulator mission, re-run offline through the same code.

Two stereo cameras

Talos has two ZED X Mini stereo cameras: forward (ffc: gate, slalom, torpedo board) and downward (dfc: bins, table). The ZED ROS wrapper publishes under /talos/<camera>/zed_node/:

  • rgb/image_rect_color/compressed: rectified left colour image, 1920×1200, JPEG;
  • depth/depth_registered: 32-bit float depth in metres, pixel-aligned with the colour image;
  • rgb/camera_info: the intrinsics.

Depth is the z coordinate in the optical frame (x right, y down, z out of the lens), not distance along the ray. Nereus's forward camera has f_x = f_y = 1864 px (54.5° × 35.7° view); the robot's calibrated one (Chapter 1) has f_x = 1701.5 px, a 59° view. Only one camera is processed at a time.

Pairing colour with depth

Depth (9.2 MB per frame) arrives well after its colour frame (a few hundred kB). "Newest depth" would pair a frame with an older view while Talos turns.

So the node buffers depth (_match_depth): up to depth_buffer_size = 15 frames, none older than max_depth_age = 1 s. Each colour frame takes the depth with the nearest stamp, or is skipped if none is within 1 s or camera info hasn't arrived. Colour and depth run in separate callback groups, so slow inference never stalls the buffer.

Detections carry the colour image's stamp (use_incoming_timestamp). Mapping looks up the camera pose at that stamp (Chapter 7), so detector latency costs time, not accuracy.

The network

Each camera has its own Ultralytics YOLO26n-seg model ("nano" size, 640×640 input, the frame letterboxed down, stride 32). Per object it returns a class, confidence, box and mask (an outline of its pixels). The forward model knows eleven classes, the downward eight:

Confidence0.650.8drops weak boxes (ffc_threshold, dfc_threshold)
IoU0.70.9same-class boxes overlapping more than this: keep the more confident

The detector is sometimes wrong

On the gate frame the network is 85 % sure the gate's right leg is a slalom pole. The detector can't tell: it has no idea where Talos is on the course.

So the system doesn't need a perfect detector. Mapping only fuses its targets (objects autonomy asked for, Chapter 9) and rejects detections that disagree with the map (Chapter 7). Through the gate, autonomy also locks the map (lock_map), so the fake pole never reaches it.

TensorRT, with a way out

On the Jetson Orin the model runs as a TensorRT engine (the network compiled for that GPU, much faster than PyTorch). YoloModel._initialize:

  • .engine next to the .pt and CUDA: load the engine;
  • export: true and CUDA: build the engine, falling back to PyTorch if export fails (usually an Ultralytics/TensorRT version mismatch);
  • no CUDA: warn and run the .pt on the CPU.

An engine is tied to the GPU and TensorRT version that built it; rebuild it on the machine that runs it.

Switching cameras

Autonomy calls set_camera_is_dfc (a SetBool, true = downward). The switch must replace the model, class map, thresholds, topics, frame id and torpedo logic all at once, or a frame could publish wrong names.

So the service only sets a 0.1 s timer. The timer (setup_camera) loads the new model, swaps every field under _camera_lock, clears the depth buffer and replaces the subscriptions. Callbacks drop messages from the old camera. An InvalidHandle from rclpy during the swap is caught and the message dropped.

Two more services: set_slalom_type renames the slalom detection, and set_table_pair_enabled merges warning + helmet into one table detection (off in the current tree; mapping fits the table from the baskets, Chapter 5).

What gets published

One vision_msgs/Detection3DArray per frame on /talos/detected_objects, stamped with the image stamp and optical frame. Each Detection3D has the class name ("pill", "torpedo", ...), confidence, and a pose whose +z axis is the surface normal, pointing back at the camera. Covariance is zero: mapping decides how much to trust it (Chapter 6).

Debug outputs, built only when subscribed: the annotated image (~/annotated/compressed), a point cloud of pose samples (~/point_cloud) and normal arrows (~/visualization_marker_array).
