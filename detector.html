Chapter 1

Cameras and the detector

Everything Talos knows about the course starts as a colour image and a depth image from one of two stereo cameras. One node, yolo_orientation, turns each pair into a list of named objects with 3D poses.

The node lives in the tensor_detector package. It is split the way this chapter and the next two are: yolo_orientation.py is the ROS side (parameters, subscriptions, the camera switch, publishing), yolo_model.py wraps the neural network, and detection.py turns the network's output into poses. This chapter covers the first two. Every frame on these pages was rendered by the Nereus simulator during a full autonomous mission and re-run offline through the same code.

Two stereo cameras

Talos carries two ZED X Mini stereo cameras: the forward camera (ffc) looks ahead at the gate, slalom and torpedo board, and the downward camera (dfc) looks at the floor for the bins and the table. Each one runs the ZED SDK under the ZED ROS wrapper, which does the stereo matching on the GPU and publishes, under /talos/<camera>/zed_node/:

  • rgb/image_rect_color/compressed: the left camera's rectified colour image, 1920×1200, JPEG-compressed;
  • depth/depth_registered: a 32-bit float depth image in metres, registered to the left image, so pixel (u, v) of the depth image is the depth of pixel (u, v) of the colour image;
  • rgb/camera_info: the intrinsics of the rectified image.

Depth here is the z coordinate in the camera's optical frame, talos/ffc_left_camera_optical_frame (x right, y down, z out of the lens), not the distance along the ray. Nereus's forward camera reports a focal length of f_x = f_y = 1864 px with the principal point near the image centre, which makes the field of view 54.5° across and 35.7° tall. Underwater the effective focal length is longer than in air, because the flat port bends each ray toward the axis; that is why the package README's first suggestion for orientations that come out slightly off is to check the camera is using the right calibration file.

Only one camera is processed at a time. The node subscribes to the active camera's three topics and nothing else; autonomy switches cameras when a task needs the other one (below).

Pairing colour with depth

The colour image and the depth image of one capture are published separately, and they do not arrive together. Depth is the heavy one (9.2 MB per frame uncompressed, against a few hundred kB of JPEG) and it reaches the node well after the colour frame it belongs to. Using "the newest depth image" for each colour frame would therefore pair it with depth from an earlier capture, and while Talos turns, every pixel of that older depth image belongs to a slightly different view.

The node keeps a ring buffer of recent depth frames instead (depth_callback, _match_depth): at most depth_buffer_size = 15 frames, and none older than max_depth_age = 1 s behind the newest. Each colour frame takes the buffered depth frame whose header stamp is nearest its own, and is skipped if that is more than 1 s away or the camera info has not arrived yet. The colour and depth callbacks sit in separate mutually exclusive callback groups on a multi-threaded executor, so a slow inference never holds up the depth subscription and the buffer stays current.

The stamp that goes out with the detections is the colour image's (use_incoming_timestamp), the moment the picture was taken, not the moment processing finished. Mapping looks up where the camera was at exactly that stamp (Chapter 5), so latency in the detector costs time but not accuracy.

The network

The detector is a YOLO instance-segmentation network: for each object it finds it returns a class, a confidence, a bounding box and a mask, an outline of the object's pixels. Talos runs two of them, one per camera, both Ultralytics YOLO26n-seg: the "nano" size, a 640×640 input (the 1920×1200 frame is letterboxed down to it), stride 32. Two thresholds apply. Confidence (ffc_threshold 0.65, dfc_threshold 0.8) drops weak detections. IoU (0.7 and 0.9) is the non-maximum-suppression overlap: of two boxes of the same class that overlap by more than this fraction, only the more confident survives. The downward camera's 0.9 keeps two overlapping boxes of one class unless they are near-duplicates. Both thresholds are passed to the network, and the node checks confidence once more on each box; the second check is redundant but harmless.

TensorRT, with a way out

On Talos's Jetson Orin the model runs as a TensorRT engine: the network compiled and optimised for that specific GPU, much faster than running it through PyTorch. YoloModel._initialize handles the three cases:

  • an .engine file next to the .pt and CUDA available: load the engine;
  • export: true and CUDA available: build the engine from the .pt, then load it. If the export fails, typically because the installed Ultralytics and TensorRT versions disagree, fall back to the PyTorch model exactly as if export were off;
  • no CUDA (a laptop without an NVIDIA GPU): warn and run the .pt on the CPU.

An engine is tied to the GPU and the TensorRT version that built it. Nereus runs the stack on a desktop RTX card with the engine file from the robot's workspace, and TensorRT says so on start-up ("Using an engine plan file across different models of devices is not recommended"). It works, but rebuilding the engine on the machine that runs it is the safe path.

Switching cameras

Autonomy picks the camera with the set_camera_is_dfc service (a SetBool: true for the downward camera). The switch has to replace a lot of state at once: the model, its class map and thresholds, the topic prefix, the frame id the detections are stamped with, and whether the torpedo logic runs. A frame processed halfway through, say with the downward model but the forward camera's class map, would publish confidently wrong names.

So the service only records the request and sets a 0.1 s timer; the timer callback (setup_camera) loads the new model first, then swaps every field together under _camera_lock, clears the depth buffer, and replaces the subscriptions. Each subscription callback is bound to the camera it was created for (functools.partial(..., camera=camera)), and drops any message whose camera is no longer the active one: messages already in flight from the old camera can't leak into the new configuration. Destroying a subscription while an executor thread is taking a message from it raises InvalidHandle inside rclpy; the node's spin loop recognises that one case and drops the message instead of crashing.

Two more services tune the processing without a switch: set_slalom_type renames the published slalom detection, and set_table_pair_enabled turns the warning + helmet pair into one table detection (Chapter 3).

What gets published

One message per frame goes to mapping: /talos/detected_objects, a vision_msgs/Detection3DArray stamped with the image's stamp and the camera's optical frame. Each Detection3D in it carries one hypothesis: the class name as a string ("pill", "torpedo", "fire_hole_large"), the confidence, and a pose: the object's centre in the camera frame and an orientation whose +z axis is the object's surface normal, pointing back at the camera. The pose's covariance is left at zero. The detector says where it saw something, and mapping decides how much to believe it, from where the object was in the image and how Talos was moving (Chapter 4).

Three more outputs exist for people, and cost nothing unless someone subscribes: the annotated image (~/annotated/compressed, the network's own drawing of boxes and masks), a point cloud of every 3D sample the pose fits used (~/point_cloud, coloured by class) and RViz markers, an arrow along each normal (~/visualization_marker_array, cleared and redrawn each frame). The node checks the subscriber count of each before building it.
