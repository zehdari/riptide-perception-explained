Your turn · Chapter 11

Working on it yourself

Everything in this site came out of a simulator run you can repeat on any team machine with the workspace built. This chapter is the recipe: run it, break it, measure it, change it.

The short version
  • Nereus runs Talos's real stack, perception and mapping included. Start a Zenoh router, launch sim.launch.py, press Enable, start a tree.
  • You can move the course away from Talos's map with a scenario file, to see how mapping copes.
  • Record a bag, then turn it into numbers and plots with the scripts in this site's tools/.
  • Almost everything tunable is in two YAML files: riptide_mapping/config/config.yaml and tensor_detector/config/yolo_orientation.yaml.
  • Change one thing at a time, rerun the same scenario, compare. Then do it on the robot.

Set up a shell

Every terminal below starts the same way. The UWRT stack uses Zenoh as its ROS middleware.

source /opt/ros/humble/setup.bash
source ~/osu-uwrt/release/install/setup.bash
source ~/osu-uwrt/release/nereus/build/ros-viewer/ros/setup.bash
export RMW_IMPLEMENTATION=rmw_zenoh_cpp

Nereus itself has to be built once (~/osu-uwrt/release/nereus/build.sh, see its README), and the workspace with colcon build as usual.

Run the stack in Nereus

In one terminal, the Zenoh router; in another, the simulator, the viewer and the whole robot stack:

ros2 run rmw_zenoh_cpp rmw_zenohd

ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim

mpc_model:=sim gives the MPC an exact copy of the simulated vehicle, so the control is not the thing you are debugging. Wait for the detector to log that its TensorRT engine is loaded (the first start exports the engine and takes a few minutes). Then, in the viewer:

  1. Press Enable (top left). The viewer owns the kill switch in sim; nothing moves until you do.
  2. In Autonomy, pick a tree (RepairCompMpcTree runs the whole competition) and press Start.
  3. Turn on Covariance in the toolbar to see mapping's ellipsoids, and Display → Mapping ghost to see mapping's estimate drawn over the true course.

To run a tree from a script instead (what the runs in Chapter 10 used), with this site's checkout:

python3 tools/nereus/run_tree.py \
  ~/osu-uwrt/release/src/riptide_autonomy/trees/RepairCompMpcTree.xml /tmp/run.json 2400

It sends the tree to /talos/autonomy/run_tree and writes the subtree stack it saw to the JSON. You still press Enable in the viewer.

Move the course

By default Nereus puts every prop exactly where Talos's map says, which hides most of what mapping does. A scenario file moves them. tools/nereus/shifted_scenario.yaml is the moved course from Chapter 10: everything 0.6 m east and 0.4 m south, the torpedo another 0.9 m and 0.9 m. Edit the task_placements, then copy it into Nereus's pack folder, because pack paths inside it must be relative (an absolute path is rejected):

mkdir -p ~/osu-uwrt/release/nereus/content/packs/scenarios/my_course
cp tools/nereus/shifted_scenario.yaml \
   ~/osu-uwrt/release/nereus/content/packs/scenarios/my_course/scenario.yaml
ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim \
  scenario:=$HOME/osu-uwrt/release/nereus/content/packs/scenarios/my_course

Good experiments: shift everything by the same amount (mapping should find the offset from the first prop it sees); move one prop a metre (it should be released, Chapter 8, and see Chapter 10 for when it isn't); turn the whole course 3° about the start (the course yaw).

Record what happened

A bag of these topics is everything the site's plots need, about 3 MB/s with the annotated images:

ros2 bag record -o mission --use-sim-time -e \
 '^/talos/(mapping/.*|detected_objects|yolo_orientation/annotated/compressed|state/mapping|simulator/ground_truth|odometry/filtered|autonomy/tree_stack|state/kill)$|^/tf$|^/tf_static$'

Save mapping's and the tree's log lines too, they are the most readable record of what happened: ros2 launch ... 2>&1 | tee run.log. Then, from this site's checkout:

python3 tools/bag_to_mission.py mission /tmp/nereus_sim/<run>/resolved.json mission.json --log run.log
python3 tools/hero_data.py mission.json hero.json      # the top-down replay's data
python3 tools/mission_data.py ...                      # Chapter 10's error and offset series

bag_to_mission.py puts every detection into the map frame with TF at its timestamp, keeps each object's published estimate and covariance, the map → offset transform, the targets and the tree's stack, and the simulator's true course from resolved.json (Nereus writes it to the run's output folder). The script's docstring lists what it writes.

Poke at mapping while it runs

Mapping is just topics and services, so you can drive it by hand. With the map unlocked and something in view:

ros2 topic echo /talos/mapping/torpedo --once          # estimate + covariance
ros2 topic echo /talos/mapping/fused                   # what each detection was fused into
ros2 topic echo /talos/state/mapping                   # current targets and lock
ros2 topic hz /talos/detected_objects                  # detector rate (about 10 Hz in Nereus)

ros2 service call /talos/mapping_target riptide_msgs2/srv/MappingTarget \
  "{target_info: {target_object: 'torpedo', lock_map: false}}"
ros2 service call /talos/mapping/set_background_targets riptide_msgs2/srv/SetString "{data: 'helmet,warning'}"
ros2 service call /talos/mapping/reset_mapping std_srvs/srv/Trigger
ros2 service call /talos/set_camera_is_dfc std_srvs/srv/SetBool "{data: true}"   # down camera

Mapping's own log says when anything important happens: 4 detections agree, 30 rejections in a row … reacquiring, prior disagrees with the other props, released. Set the log level to debug to see every rejected detection and why.

Mapping reads estimator.* and noise.* again whenever a parameter changes, so ros2 param set /talos/riptide_mapping2 estimator.acquire_detections 3 takes effect at once. A changed prior moves that object immediately; a changed parent waits for mapping/reset_mapping.

A tuning recipe

  1. Measure the detection noise. Hold Talos still in front of a prop at three or four ranges for 15 s each and compute the scatter, as Chapter 6 did in Nereus (tools/nereus/tour.py places and holds the robot; tools/noise_measure.py computes the scatter). Do it on the robot, in the pool. Set noise.* so the model's curves sit a little above what you measured.
  2. Measure the drift. Swim a long loop that passes one prop twice, and look at how far the second sighting lands from the first. That is the odometry drift over the distance in between; set drift_var_per_m_xy from it. Too large, and mapping explains layout errors as drift (Chapter 10); too small, and it won't follow real drift.
  3. Check the layout error. After a run, compare each prop's deviation with layout_std_xy. If a prop is routinely more than a metre off, measure it again rather than widen the prior.
  4. Rerun the same scenario after each change and compare the errors, not just whether the tree succeeded: every task fails soft, so a tree can succeed with half its props wrong.

Test before you push

The estimator has no ROS in it, so its tests run anywhere:

cd ~/osu-uwrt/release/src/riptide_perception/riptide_mapping
python3 -m pytest -q test/test_map_estimator.py

If you change map_estimator.py, this site's copy of it (src/engine/estimator.js) is checked against the Python by npm test, using scenarios recorded by tools/golden.py; rerun both, and the site's figures stay honest.

Retrain the detector

Chapter 2 walks through it: record the props, label masks, add Nereus's synthetic images, augment, train, export. To try a new model in the sim, drop the .pt into tensor_detector/weights/, point ffc_model or dfc_model at it with its class map, rebuild, and run the same scenario. The detector exports a TensorRT engine on first start. Then compare: the same tree, the same course, and how many detections each prop gets and from how far.
