Your turn · Chapter 11

Working on it yourself

Everything on this site came from a simulator run you can repeat on any team machine. Here is the recipe: run it, break it, measure it, change it.

The short version
  • Nereus runs Talos's real stack. Start a Zenoh router, launch sim.launch.py, press Enable, start a tree.
  • Move the course with a scenario file; record a bag; plot it with this site's tools/.
  • Almost everything tunable is in riptide_mapping/config/config.yaml and tensor_detector/config/yolo_orientation.yaml.
  • Change one thing, rerun the same scenario, compare. Then try it on the robot.

Set up a shell

Start every terminal with this (the stack uses Zenoh as its ROS middleware):

source /opt/ros/humble/setup.bash
source ~/osu-uwrt/release/install/setup.bash
source ~/osu-uwrt/release/nereus/build/ros-viewer/ros/setup.bash
export RMW_IMPLEMENTATION=rmw_zenoh_cpp

Build Nereus once (~/osu-uwrt/release/nereus/build.sh, see its README) and the workspace with colcon build.

Run the stack in Nereus

The router in one terminal, the simulator and stack in another:

ros2 run rmw_zenoh_cpp rmw_zenohd

ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim

mpc_model:=sim gives the MPC an exact vehicle model. Wait for the detector's TensorRT engine to load (a few minutes the first time). Then, in the viewer:

  1. Press Enable (top left), the sim's kill switch.
  2. In Autonomy, pick a tree (RepairCompMpcTree is the full competition) and press Start.
  3. Turn on Covariance (mapping's ellipsoids) and Display → Mapping ghost (the estimate over the true course).

Or run a tree from a script, as Chapter 10 did:

python3 tools/nereus/run_tree.py \
  ~/osu-uwrt/release/src/riptide_autonomy/trees/RepairCompMpcTree.xml /tmp/run.json 2400

It sends the tree to /talos/autonomy/run_tree; you still press Enable.

Move the course

By default props sit exactly where the map says. tools/nereus/shifted_scenario.yaml is Chapter 10's moved course. Edit its task_placements and copy it into Nereus's pack folder (pack paths must be relative):

mkdir -p ~/osu-uwrt/release/nereus/content/packs/scenarios/my_course
cp tools/nereus/shifted_scenario.yaml \
   ~/osu-uwrt/release/nereus/content/packs/scenarios/my_course/scenario.yaml
ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim \
  scenario:=$HOME/osu-uwrt/release/nereus/content/packs/scenarios/my_course

Try: shift everything equally (mapping should find the offset from the first prop); move one prop a metre (it should be released, Chapter 8); turn the course 3° about the start.

Record what happened

These topics are all the plots need (about 3 MB/s):

ros2 bag record -o mission --use-sim-time -e \
 '^/talos/(mapping/.*|detected_objects|yolo_orientation/annotated/compressed|state/mapping|simulator/ground_truth|odometry/filtered|autonomy/tree_stack|state/kill)$|^/tf$|^/tf_static$'

Save the logs too: ros2 launch ... 2>&1 | tee run.log. Then:

python3 tools/bag_to_mission.py mission /tmp/nereus_sim/<run>/resolved.json mission.json --log run.log
python3 tools/hero_data.py mission.json hero.json      # the top-down replay's data
python3 tools/mission_data.py ...                      # Chapter 10's error and offset series

resolved.json, the true course, is in Nereus's run output folder. The script's docstring lists what it writes.

Poke at mapping while it runs

Mapping is just topics and services. With the map unlocked and something in view:

ros2 topic echo /talos/mapping/torpedo --once          # estimate + covariance
ros2 topic echo /talos/mapping/fused                   # what each detection was fused into
ros2 topic echo /talos/state/mapping                   # current targets and lock
ros2 topic hz /talos/detected_objects                  # detector rate (about 10 Hz in Nereus)

ros2 service call /talos/mapping_target riptide_msgs2/srv/MappingTarget \
  "{target_info: {target_object: 'torpedo', lock_map: false}}"
ros2 service call /talos/mapping/set_background_targets riptide_msgs2/srv/SetString "{data: 'helmet,warning'}"
ros2 service call /talos/mapping/reset_mapping std_srvs/srv/Trigger
ros2 service call /talos/set_camera_is_dfc std_srvs/srv/SetBool "{data: true}"   # down camera

Watch the log for 4 detections agree, 30 rejections in a row … reacquiring and prior disagrees with the other props, released. Debug level shows every rejection.

estimator.* and noise.* apply live, e.g. ros2 param set /talos/riptide_mapping2 estimator.acquire_detections 3. A changed prior applies at once; a changed parent waits for mapping/reset_mapping.

A tuning recipe

  1. Measure detection noise on the robot: hold still at 3–4 ranges for 15 s each (tools/nereus/tour.py, tools/noise_measure.py, as in Chapter 6). Set noise.* a little above the measured scatter.
  2. Measure drift. Swim a long loop past one prop twice; the gap between sightings sets drift_var_per_m_xy. Too large blames layout errors on drift (Chapter 10); too small won't follow real drift.
  3. Check layout error against layout_std_xy. A prop routinely over a metre off should be re-measured, not given a wider prior.
  4. Rerun the same scenario and compare errors: a tree can succeed with half its props wrong.

Test before you push

The estimator has no ROS in it, so its tests run anywhere:

cd ~/osu-uwrt/release/src/riptide_perception/riptide_mapping
python3 -m pytest -q test/test_map_estimator.py

If you change map_estimator.py, also run npm test here: it checks the site's copy (src/engine/estimator.js) against scenarios recorded by tools/golden.py.

Retrain the detector

Training is Chapter 2. To try a model in the sim: drop the .pt in tensor_detector/weights/, point ffc_model or dfc_model at it with its class map, rebuild, and rerun the same scenario. Compare detections per prop, and from how far.
