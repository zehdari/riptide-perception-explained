Mapping · Chapter 8

The course map

Talos starts every run already knowing roughly where every prop is. Mapping's job is to work out how far that knowledge is off: one shift for the whole course, plus a small correction for each prop, estimated from every sighting so far.

The short version
  • Talos starts with a map of where every prop should be (measured by hand at the pool). Two things make it wrong: the robot's own position estimate drifts, and some props are placed differently than measured.
  • Mapping models both: one shared offset for the whole course (drift, or a map measured from the wrong spot), and a small deviation per prop (that prop measured wrong).
  • Seeing one prop can't tell which it is, so the difference is split by how likely each is. Seeing a second prop that agrees pins the offset, and every prop not yet seen moves with it.
  • A prop that disagrees with the others should be released: it stops moving the map. The solve uses a robust penalty so one bad prop can't drag everything, though Chapter 10 shows a case where it still did.

Chapter 7 tracked one object from its detections. That alone would be enough if Talos only ever looked at what was in front of it. It isn't: autonomy drives to the torpedo board before the camera has seen it, so mapping has to say where the board is from what it knows about the gate and the slalom. This chapter is about that, the part of map_estimator.py that ties every map object together. The file has no ROS in it, so its unit tests (test/test_map_estimator.py) run it on their own, and the browser runs a JavaScript copy of it checked against the Python on recorded scenarios.

Why a map at all

Before a competition run the team measures the course: the gate, the slalom, the torpedo board, the bins and the table, each with a position and a heading. These go into init_data in mapping's config/config.yaml. The config calls the layout dead-reckoned: the positions come from odometry, not a survey, so they are only as good as that odometry was on the day.

Then two things go wrong. During the run, Talos's own odometry (an EKF on the DVL, the fibre-optic gyro and the depth sensor) drifts: a few centimetres per ten metres, but it adds up over a course twenty metres long. And the layout itself is sometimes off: a prop was moved after it was measured, or the measurement was bad. The first error is shared by every prop. The second belongs to one prop. Mapping estimates both.

What mapping does not do is estimate Talos's own position. It trusts odometry over short distances and asks a narrower question: where does the course sit in the odometry frame right now? That is a few dozen numbers rather than a full SLAM problem, small enough to solve from scratch many times a second.

One shift for the course, one correction per prop

Every map-parented object i (the gate, the slalom, the torpedo board, the bins, the table and the waypoints between them) is modelled as its prior position, turned by a small course yaw, plus an offset shared by the whole course, plus a deviation of its own:

\bp_i = \Rm(\psi)\,\bp_i^{\,0} + \bo + \bd_i
  • \bp_i^{\,0} is the prior from init_data.
  • \bo, the offset, is where the course sits in the odometry frame: one 3-vector for the whole course. Mapping publishes it as the TF map → offset, and every map object's frame hangs off offset.
  • \bd_i, the deviation, is how far the layout is off for that one prop.
  • \psi, the course yaw, is a start-heading misalignment between the layout and odometry, a rotation about the map origin. The AprilTag calibration (Chapter 9) sets Talos's heading against the board on the wall, so it is small.

Each gets a prior from the estimator block of the config:

QuantityPriorParameter
Offset at the startσ = 1.0 m in x, y; 0.3 m in zoffset_std_xy, offset_std_z
Offset drift+0.002 m² per metre travelled, +10⁻⁵ m² per second (xy); a tenth of that in zdrift_var_per_m_xy, drift_var_per_s_xy
Deviationσ = 0.25 m in x, y; 0.15 m in z, heavy-tailedlayout_std_xy, layout_std_z, layout_robust_scale = 2
Course yawσ = 2°course_yaw_std_deg

The offset is a random walk in distance travelled: dead-reckoning error grows with how far Talos has moved, not with time, so its variance grows by 0.002 m² per metre. After the 20 m to the torpedo board that is σ ≈ 0.2 m on top of the start uncertainty; after the 60 m of a whole run, about 0.35 m. A small per-second term keeps it growing even while Talos holds station. Mapping measures distance by summing the steps between odometry messages and ignoring any jump over 1 m, which is a reset rather than travel (odom_callback).

The deviation prior says layout errors are small: a quarter of a metre is typical. A prop that was moved by a metre is a different kind of mistake, and the next sections are about not letting one bad prop drag the whole map.

From tracks to fixes

The filter in Chapter 7 keeps one track per object in the odometry frame. Once a map object's track has gate_min_updates = 10 accepted detections, it becomes a fix: a measurement of where that object was, stamped with the odometry distance and time at which it was last seen (observe). While Talos keeps looking at the object, the fix is live: it improves with each detection and its distance stamp moves forward.

When autonomy retargets the object later (a new mapping_target call), the live fix is frozen: it stops changing and a new track starts from where the map has the object (_freeze). That is how a revisit measures drift. The gate seen at the start and the gate seen again on the way home are two fixes of the same object, taken 60 m of odometry apart. Same prop, same deviation, so whatever moved between them is the offset.

Two fixes of one object less than fix_merge_distance = 1 m of travel apart say the same thing and are merged, in information form, so retargeting the same prop over and over doesn't pile up near-duplicates:

\P = \left(\P_a^{-1} + \P_b^{-1}\right)^{-1}, \qquad \bz = \P\left(\P_a^{-1}\bz_a + \P_b^{-1}\bz_b\right)

The solve

Every time the fixes change, mapping solves for all the unknowns at once (_solve). The fixes are sorted by odometry distance, and each fix k gets an offset node \bo_k of its own: the offset at the moment that fix was taken. Each object that has a fix gets a deviation \bd_i. With the course yaw, that is 1 + 3K + 3N unknowns for K fixes of N objects, around 40 on a full run.

The cost has four kinds of terms. Each fix \bz_k, with covariance \P_k from its track, should match the model; consecutive offset nodes should differ by no more than the drift between them, \Q_k = \Q(\Delta s_k, \Delta t_k); the first node is tied to the start prior; and the yaw and the deviations pay their priors:

J = \frac{\psi^2}{\sigma_\psi^2} + \sum_k \big\|\bz_k - \Rm(\psi)\bp^{\,0}_{i(k)} - \bo_k - \bd_{i(k)}\big\|^2_{\P_k^{-1}} + \|\bo_1\|^2_{(\boldsymbol\Sigma_o + \Q_1)^{-1}} + \sum_{k} \|\bo_{k+1} - \bo_k\|^2_{\Q_{k}^{-1}} + \sum_i \rho\!\left(\|\bd_i\|^2_{\boldsymbol\Sigma_L^{-1}}\right)

‖v‖²W = vᵀWv. Σo is the start-offset prior, ΣL the layout prior, Q(Δs, Δt) = diag(0.002 Δs + 10⁻⁵ Δt, …) the drift. ρ is the robust penalty of the next section.

Only the course yaw makes it nonlinear, through \Rm(\psi). The code linearizes it about the current guess, \Rm(\psi)\bp \approx \Rm(\hat\psi)\bp + \mathbf g\,(\psi - \hat\psi) with \mathbf g = \partial(\Rm\bp)/\partial\psi, builds the normal equations \mathbf A\bx = \mathbf b and solves them with a dense solve, iterating until no unknown moves by more than 10⁻⁷ (at most 30 times). A 40×40 system is nothing to solve. The inverse of \mathbf A at the answer is the covariance of every unknown, and that is what makes the published covariances mean something.

The current offset is the newest node, with the drift since that fix added to its covariance (offset). Every map object is then predicted from the solution (_predicted):

\hat\bp_i = \Rm(\hat\psi)\,\bp_i^{\,0} + \hat\bo + \hat\bd_i, \qquad \boldsymbol\Sigma_i = \mathbf J\,\mathbf A^{-1}_{[\psi,\bo,\bd_i]}\,\mathbf J^\top + \Q(\Delta s, \Delta t)\;\big[\,+\,\boldsymbol\Sigma_L\big]

For an object that has never been seen there is no \hat\bd_i, so it gets the layout prior \boldsymbol\Sigma_L added instead: an unseen prop is never surer than "where the layout says, moved with the course, give or take 25 cm". That is the estimate autonomy drives to before the camera has the prop.

One sighting can't tell the two apart

Suppose the first prop Talos sees, the gate, is 0.6 m from its prior. Either the course sits 0.6 m off in odometry, or the gate was measured wrong. One fix can't separate the two: \bo + \bd_\text{gate} is all it constrains. The solve splits the difference by the priors. The offset is the more uncertain (σ = 1 m against 0.25 m), so about 94 % of the shift goes to the offset, and every other prop moves with it. That is the right call for the first prop: the start offset really is the bigger unknown.

The second prop settles it. If the slalom is also 0.6 m off in the same direction, the shift is the offset: two props explaining it with one shared vector is far cheaper than two deviations. If the slalom sits exactly on its prior, the gate's 0.6 m must be the gate's own, and the offset goes back. A prop that disagrees is released

If the deviation prior were Gaussian, a torpedo board placed 1.5 m from its prior would pull the offset, and with it every other prop, a good fraction of the way toward itself. Three props that agree would be overruled in part by one that doesn't. So the layout term is heavy-tailed. Instead of the squared Mahalanobis distance r_i^2 = \|\bd_i\|^2_{\boldsymbol\Sigma_L^{-1}}, each deviation pays a Cauchy penalty with scale s = layout_robust_scale = 2:

\rho(r^2) = s^2 \log\!\left(1 + \frac{r^2}{s^2}\right), \qquad w(r^2) = \frac{1}{1 + r^2/s^2}

Near zero it is the Gaussian r^2. Far out it grows only logarithmically: past about 2σ, moving a deviation further barely costs anything more, so the solve would rather blame the prop than move the offset. The weight w is how much of the Gaussian pull is left. The solve is iteratively reweighted least squares: solve with the layout terms scaled by their weights, recompute the weights from the new deviations, solve again (weights, run).

A robust cost has more than one local minimum: "the torpedo is off" and "the gate and the slalom are off" can both be stable answers. IRLS started from zero can settle in the wrong one. So whenever the set of fixes changes (a new fix, or one frozen), the solve runs several times: once from zero, once more from zero blaming each prior in turn (that prop's first weight set to zero, every other to one), and once from the previous answer. It keeps the start with the lowest true robust cost (lines 578–590). When only a live fix moved (one more detection of the object in view), it continues from the last answer for up to 8 iterations, which is what runs at detection rate.

A map object whose weight is below one half (its deviation is more than s = 2 layout σ, 50 cm, from its prior) is released: its prior has stopped moving the map. Mapping logs when that changes (report_released_priors):

[WARN] torpedo's prior disagrees with the other props, released (it no longer moves the map)
[INFO] torpedo's prior agrees with the other props again

Releasing is not throwing away. The released prop's own fixes still place it, so its estimate is where it was seen; it mostly stops pulling the offset. Mostly: the Cauchy pull fades but never reaches zero, so in the blame figure a torpedo board moved 1.5 m (weight 0.12) still drags the offset about 13 cm its way. With a Gaussian prior it would drag it 67 cm. And because the weight is recomputed every solve, a prop released early, when it was the only evidence against two others, comes back if later fixes show the others were the odd ones out.

The course yaw comes out of the same solve. One prop can't tell a rotation from a shift. Two props at different bearings from the map origin can: a rotation moves the far one more. With the 2° prior the yaw only moves when several props agree on it, which is what a heading error from the calibration would look like.

In Nereus

On the robot, nothing tells mapping the truth. In Nereus the simulator knows where every prop is, so the estimate can be scored against it.

What it assumes

  • Odometry drift is a translation. The offset has no rotation of its own, only the one course yaw at the start. A heading that drifts during the run shows up as offsets that disagree between distant props, which the deviations then absorb. Talos's fibre-optic gyro keeps heading drift small, which is why this is reasonable.
  • The vehicle's own track is not estimated. A fix is stamped with odometry distance and time, not with a vehicle pose. Between fixes only the drift model connects them.
  • Only map-parented objects are in the solve. Torpedo holes, gate halves, slalom poles and table items live in their parent's frame with a three-state filter each (Chapter 7) and move with their parent.
  • Only targeted objects establish themselves. A background object (seen while searching for something else) still gets fused, but its first time as the target starts a fresh search, so a far, oblique background estimate is never trusted as confirmed.
