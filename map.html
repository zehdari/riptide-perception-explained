Mapping · Chapter 8

The course map

Talos starts every run knowing roughly where every prop is. Mapping works out how far off that is: one shift for the whole course, plus a small correction per prop.

The short version
  • Talos starts with a hand-measured map of the course. Odometry drift and misplaced props make it wrong.
  • Mapping estimates one shared offset (where the course sits in odometry) and a small deviation per prop.
  • One sighting can't tell the two apart; a second prop that agrees pins the offset, and unseen props move with it.
  • A prop that disagrees is released and mostly stops moving the map (Chapter 10 shows where it still did).

Autonomy drives to the torpedo board before the camera has seen it, so mapping must place it from the gate and the slalom. That is map_estimator.py. It has no ROS in it, so its unit tests run it alone, and the browser runs a JavaScript copy checked against the Python.

Why a map at all

Before a run the team measures each prop's position and heading into init_data in config.yaml. The layout is dead-reckoned (measured with odometry, not surveyed). Two things go wrong:

  • Drift. Odometry (an EKF on the DVL, fibre-optic gyro and depth sensor) drifts a few centimetres per ten metres. Shared by every prop.
  • Layout errors. A prop was moved or measured badly. Belongs to one prop.

Mapping doesn't estimate Talos's own position. It only asks where the course sits in the odometry frame: a few dozen numbers, solvable many times a second.

One shift for the course, one correction per prop

Every map-parented object i (gate, slalom, torpedo board, bins, table, waypoints) is its prior, turned by a small course yaw, plus a shared offset, plus its own deviation:

\bp_i = \Rm(\psi)\,\bp_i^{\,0} + \bo + \bd_i
  • \bp_i^{\,0}: the prior from init_data.
  • \bo, the offset: one 3-vector, published as the TF map → offset; every map object's frame hangs off it.
  • \bd_i, the deviation: how far the layout is off for that prop.
  • \psi, the course yaw: start-heading misalignment about the map origin. Small, because the AprilTag calibration (Chapter 9) sets heading.

The offset is a random walk in distance travelled: σ ≈ 0.2 m extra after 20 m, about 0.35 m after a 60 m run. Odometry jumps over 1 m count as resets, not travel (odom_callback).

From tracks to fixes

  • After 10 accepted detections (gate_min_updates), a map object's track becomes a fix: a measurement stamped with odometry distance and time. It stays live while Talos keeps looking.
  • Retargeting the object freezes the fix and starts a new track (_freeze). Two fixes of one prop, 60 m of odometry apart, measure the drift between them.
  • Fixes less than fix_merge_distance = 1 m of travel apart are merged:
\P = \left(\P_a^{-1} + \P_b^{-1}\right)^{-1}, \qquad \bz = \P\left(\P_a^{-1}\bz_a + \P_b^{-1}\bz_b\right)

The solve

Whenever fixes change, mapping solves for everything at once (_solve). Each fix k gets its own offset node \bo_k, each seen object a deviation: 1 + 3K + 3N unknowns, around 40 on a full run. Fixes should match the model, consecutive offsets should differ by no more than the drift \Q_k, and the priors are paid:

J = \frac{\psi^2}{\sigma_\psi^2} + \sum_k \big\|\bz_k - \Rm(\psi)\bp^{\,0}_{i(k)} - \bo_k - \bd_{i(k)}\big\|^2_{\P_k^{-1}} + \|\bo_1\|^2_{(\boldsymbol\Sigma_o + \Q_1)^{-1}} + \sum_{k} \|\bo_{k+1} - \bo_k\|^2_{\Q_{k}^{-1}} + \sum_i \rho\!\left(\|\bd_i\|^2_{\boldsymbol\Sigma_L^{-1}}\right)

‖v‖²W = vᵀWv. Σo is the start-offset prior, ΣL the layout prior, Q(Δs, Δt) = diag(0.002 Δs + 10⁻⁵ Δt, …) the drift. ρ is the robust penalty of the next section.

Only the yaw is nonlinear. The code linearizes it, solves the normal equations \mathbf A\bx = \mathbf b densely, and iterates until nothing moves more than 10⁻⁷ (at most 30 times). \mathbf A^{-1} at the answer is the covariance of every unknown.

Every map object is then predicted from the newest offset node plus drift since (_predicted):

\hat\bp_i = \Rm(\hat\psi)\,\bp_i^{\,0} + \hat\bo + \hat\bd_i, \qquad \boldsymbol\Sigma_i = \mathbf J\,\mathbf A^{-1}_{[\psi,\bo,\bd_i]}\,\mathbf J^\top + \Q(\Delta s, \Delta t)\;\big[\,+\,\boldsymbol\Sigma_L\big]

A never-seen object has no \hat\bd_i and gets \boldsymbol\Sigma_L added: "where the layout says, moved with the course, give or take 25 cm". Autonomy drives to that.

One sighting can't tell the two apart

If the gate is 0.6 m from its prior, one fix only constrains \bo + \bd_\text{gate}. The priors split it: the offset is more uncertain (1 m vs 0.25 m), so about 94 % goes to the offset and every prop moves with it. A second prop settles it: if the slalom is also 0.6 m off, it's the offset; if it sits on its prior, it's the gate's own error.

A prop that disagrees is released

With a Gaussian layout prior, one torpedo board 1.5 m off would drag the offset, and every prop, part of the way toward it. So each deviation pays a heavy-tailed Cauchy penalty on r_i^2 = \|\bd_i\|^2_{\boldsymbol\Sigma_L^{-1}}, scale s = layout_robust_scale = 2:

\rho(r^2) = s^2 \log\!\left(1 + \frac{r^2}{s^2}\right), \qquad w(r^2) = \frac{1}{1 + r^2/s^2}

Near zero it is Gaussian; far out it grows only logarithmically, so the solve would rather blame the prop. It is solved by iteratively reweighted least squares (IRLS: solve, recompute weights w, repeat; run).

  • Several starts. A robust cost can have more than one minimum. When the fix set changes, the solve runs from zero, from zero blaming each prior in turn, and from the last answer, and keeps the lowest cost. When only a live fix moved, it continues from the last answer for up to 8 iterations.
  • Released means weight below one half (deviation over 2 layout σ, 50 cm). Mapping logs the change (report_released_priors):
[WARN] torpedo's prior disagrees with the other props, released (it no longer moves the map)
[INFO] torpedo's prior agrees with the other props again
  • A released prop is still placed by its own fixes. Its pull fades but never reaches zero: a torpedo moved 1.5 m (weight 0.12) still drags the offset about 13 cm, against 67 cm with a Gaussian.
  • Weights are recomputed every solve, so a prop released early can come back.
  • Course yaw needs two props at different bearings; with the 2° prior it only moves when several agree.

In Nereus

On the robot nothing knows the truth. In Nereus the simulator does, so the estimate can be scored.

What it assumes

  • Drift is a translation. Only the one start yaw rotates; heading drift during the run gets absorbed by deviations. The fibre-optic gyro keeps it small.
  • The vehicle's track isn't estimated. Fixes are stamped with distance and time; only the drift model connects them.
  • Only map-parented objects are solved. Holes, gate halves, slalom poles and table items move with their parent (Chapter 7).
  • Only targeted objects establish. A background estimate is never trusted as confirmed.
